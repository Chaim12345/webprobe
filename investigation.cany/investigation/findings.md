# Findings

- **fnd_1** Burp refuses a hotkey when EITHER side is taken: burp.Zfhv.ZT(III)V asserts `this.Z_.get(chord) == null` (no other action on that chord) and `this.Zp.get(actionId) == null` (that action has no chord) before it writes the two maps. A rebuild must reject both directions, not just the chord. (Seen it; evidence: ev_7dbf2c50b84b2abd63c5e2a9d791530ac9fd90e09a80d33f9f974724ef3ff761)
- **fnd_2** The hotkey settings file is authoritative, not an overlay: burp.Zfhv.Zh(Z_dk) reads it, maps the stored entries, drops later duplicates by keystroke (HashSet of ZI()), then applies them through Z_(), which first clears the whole registry via ZL(). So an action absent from the file ends up with no hotkey at all. (Seen it; evidence: ev_e199c6630d23d2f9df87cc0c3add80d5f8320325e3d630de68b7c3ad3767135f)
- **fnd_3** Class and method names can be made readable without any craft/REA rename tool: JarRemapper rewrites the jar's bytecode from a class map plus a method map, and the remapped jar then loads and runs (SuiteCommand.label()/id()/category()/commandId() verified by reflection), so craft's decompiler shows `HotkeyRegistry.applyBinding` instead of `Zfhv.ZT`. Mapping rules are in re/mapping/README.md. (Seen it; evidence: ev_9cef4b7511736beefa06286f3fb52180536afd0d473d229800f5f802cec355fa)
- **fnd_4** Burp's CA certificate is fetched through the proxy, not from disk: the browser must already be proxying through the listener, then visits http://burpsuite, which Burp itself answers. WebProbe reproduces that with http://webprobe (and the Burp host) answered locally by the proxy, serving the CA as PEM and DER. (Seen it; evidence: ev_e3e342cadafc68cecc2715b141627971ca37cdfd0290fcbce47a5c737ca73e05)
- **fnd_5** Burp verifies a working CA install by visiting any HTTPS URL and confirming there is no security warning, and notes that most users never install it because the bundled browser is preconfigured. WebProbe has no bundled browser (task L-05), so its checklist verifies by counting decrypted HTTPS exchanges in history and says so. (Seen it; evidence: ev_e3e342cadafc68cecc2715b141627971ca37cdfd0290fcbce47a5c737ca73e05)
- **fnd_6** ZKM regenerates class names per build: of the 12754 names in the earlier structural pass, only 4690 keys exist in this jar (Implementation-Version 52685), so 8064 are stale and naming must be redone per build. This build's own evidence yields 301 high-confidence names (classes implementing a burp.api.montoya.* interface, from javap on this jar) and 61 classes with runtime-decoded strings (RuntimeStringDump invoking Burp's own decryptor). Artefacts: re/mapping/build52685.tsv, string-evidence.tsv, coverage.tsv, hierarchy52685.tsv, README.md. (Worked it out; evidence: ev_b85e70b6c8cb66f62a815ac29394ccaa9a075e12b031824291afeaa3c2f509af)
- **fnd_7** Burp's Intruder extension surface is the legacy burp.IIntruderAttack, IIntruderPayloadGenerator(+Factory), IIntruderPayloadProcessor, registered through IBurpExtenderCallbacks.registerIntruderPayloadGeneratorFactory/Processor and sendToIntruder; the Montoya API adds burp.api.montoya.intruder.HttpRequestTemplate, GeneratedPayload and AttackConfiguration. WebProbe's C-03/C-04 payload types and processing rules should mirror these contracts so extensions can plug in later (K-02). (Seen it; evidence: ev_2b28cf4a66e192c1e0206147b9976d337c3bd73541cf87af0f767b8597876fcf)
